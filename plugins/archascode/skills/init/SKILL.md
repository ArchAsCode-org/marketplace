# /archascode:init

Initialize (or refresh) the Python project for an archascode consuming
project. Modeled on `terraform init`: this is the first verb the user runs
in a project directory. It writes `pyproject.toml` from the spec, creates
`.venv`, and installs deps.

Re-run `/archascode:init` whenever `spec/architecture.yml` adds or removes an
adapter under `adapters.persistence.*` or `adapters.auth` (or changes any
binding's `app_adapters.auth`) — the dep set may have shifted and the
venv needs to catch up. The failure mode if forgotten is loud
(`ModuleNotFoundError` at app start), but the fix is just to re-invoke
this skill.

After this skill runs:

- `pyproject.toml` exists with deps driven by the spec (or base deps only,
  greenfield).
- `.venv/` exists at the project root.
- All declared deps are installed.
- The app launches with `uv run python aac.py up` once `aac.py` is present
  (i.e. post-render — every render emits it unconditionally). The lifecycle
  script is invoked by file path — there is no `aac` console-script entry
  point.

This skill sits alongside `/archascode:apply` (per-iteration render loop) and
`aac.py up` (per-run app lifecycle). It is invoked **explicitly** — never
auto-triggered from another skill.

## Dependency mapping

What this skill installs:

- **Always:** `fastapi>=0.110`, `pydantic>=2.0`, `uvicorn[standard]>=0.27`
- **`adapters.persistence.sqlserver` present:** add `pymssql>=2.3.0`.
- **`adapters.persistence.postgres` present:** add `psycopg[binary]>=3.2`.
- **`jwt_bearer` auth adapter selected anywhere:** add `pyjwt[crypto]>=2.8`.
  "Selected anywhere" means `adapters.auth.id == "jwt_bearer"` OR any
  `port_bindings.<lens>.app_adapters.auth == "jwt_bearer"` — a binding
  override is enough even when the spec-level default is `noop`. The
  rendered `jwt_bearer` adapter imports PyJWT.

That's the full mapping today. Future adapters extend the table; the rule
"declare adapter in spec → re-run `/archascode:init`" stays the same.

## Preconditions

- `uv` is on PATH.

That's the only one. Everything Python-shaped the skill needs — the
interpreter and the `ruamel.yaml` library Step 3 imports — is provisioned
by uv itself (`uv run --no-project --with 'ruamel.yaml' python -`), in an
ephemeral cached environment that touches neither system python nor the
project `.venv`. The first such run downloads the wheel (and a managed
CPython if none is on PATH), so it needs network — the same class of
requirement as Step 6's `uv sync`.

## Procedure

### Step 1 — verify prerequisites

```bash
command -v uv >/dev/null 2>&1
```

If missing, print and stop:

```
uv is required but not on PATH.
Install one of:
  - macOS:  brew install uv
  - other:  curl -LsSf https://astral.sh/uv/install.sh | sh
Then re-invoke /archascode:init.
```

### Step 2 — handle existing `pyproject.toml`

Three sub-cases:

1. **File missing** → proceed to Step 3.

2. **File present and the first line starts with `# Generated by `**
   → proceed to Step 3. The skill regenerates the file, clobbering any
   edits made below the header. Users who want auto-managed deps leave
   the header alone.

3. **File present and the first line does NOT match** → print warning,
   skip to Step 6 (venv sync only):

   ```
   WARNING: pyproject.toml exists but was not generated by archascode; leaving it alone.
   Edit freely; remove the file and re-run if you want init to take
   ownership.
   ```

Detection:

```bash
if [ -f pyproject.toml ]; then
  if head -n 1 pyproject.toml | grep -q '^# Generated by '; then
    OWNED=1
  else
    OWNED=0
  fi
else
  OWNED=1   # absent counts as "we own the slot"
fi
```

### Step 3 — read spec and write `pyproject.toml`

The whole job — parse the spec, compute deps, write the file, and
scaffold a default `environments:` block when the spec declares
none — lives in one quoted-heredoc Python block. `<<'PY'` (single-quoted
delimiter) blocks all shell expansion, so the Python body needs no `\\`,
`\"`, or `\$` escaping. Python sees the script byte-for-byte. The
interpreter comes from uv: `--with 'ruamel.yaml'` supplies the one
third-party import from an ephemeral cached environment, and
`--no-project` keeps uv from discovering and syncing the project
environment first — this step runs before `pyproject.toml` exists
(greenfield) or before Step 6 has synced it, and it must not depend on
either. uv's own progress output goes to stderr, so the stdout capture
stays clean. The spec is read **once**, via `ruamel.yaml`'s round-trip
mode — the dependency-computation logic below and the `environments:`
scaffold check both operate on that same loaded object, so a spec write
(if any) and the `pyproject.toml` dependency decisions can never observe
different content. The script prints two shell-readable lines on stdout
as debug breadcrumbs: `HAS_SQLSERVER=0|1` / `HAS_POSTGRES=0|1` (the
SQL-driver-dep decisions) and `ENV_SCAFFOLDED=0|1` (whether the
`environments:` scaffold was written).

```bash
PY_OUT=$(uv run --no-project --with 'ruamel.yaml' python - <<'PY'
import os, re, sys
from ruamel.yaml import YAML

def kebab(s):
    s = (s or "").lower()
    return re.sub(r"[^a-z0-9]+", "-", s).strip("-") or "archascode-project"

def toml_escape(s):
    return (s or "").replace("\\", "\\\\").replace('"', '\\"').replace("\n", " ").strip()

name = "archascode-project"
version = "0.0.0"
description = ""
has_sqlserver = False
has_postgres = False
has_jwt_bearer = False
env_scaffolded = False

yaml = YAML(typ="rt")
yaml.preserve_quotes = True
yaml.indent(mapping=2, sequence=4, offset=2)  # matches this repo's spec style
yaml.width = 4096  # avoid re-wrapping long lines on dump

if os.path.exists("spec/architecture.yml"):
    try:
        with open("spec/architecture.yml") as f:
            spec = yaml.load(f) or {}
    except Exception as e:
        print(f"spec parse error: {e}", file=sys.stderr)
        sys.exit(2)
    meta = spec.get("metadata") or {}
    adapters = (spec.get("adapters") or {}).get("persistence") or {}
    name = kebab(meta.get("name"))
    version = meta.get("version") or version
    description = toml_escape(meta.get("description"))
    has_sqlserver = "sqlserver" in adapters
    has_postgres = "postgres" in adapters

    # jwt_bearer can be the spec-level default auth adapter OR an override
    # in any binding's app_adapters.auth (the binding override wins even
    # when adapters.auth.id is noop). Either selection pulls in PyJWT.
    auth_default = ((spec.get("adapters") or {}).get("auth") or {}).get("id")
    binding_auths = [
        ((b or {}).get("app_adapters") or {}).get("auth")
        for b in ((spec.get("port_bindings") or {}).values())
    ]
    has_jwt_bearer = "jwt_bearer" in ([auth_default] + binding_auths)

    # Scaffold a minimal 'dev' environment when the spec
    # declares none, via the same round-trip object — comments, key order,
    # and formatting elsewhere in the file are preserved by ruamel's dumper.
    if not spec.get("environments"):
        spec["environments"] = {"dev": {"port_binding": "memory"}}
        spec["default_environment"] = "dev"
        try:
            with open("spec/architecture.yml", "w") as f:
                yaml.dump(spec, f)
        except Exception as e:
            print(f"spec write error: {e}", file=sys.stderr)
            sys.exit(2)
        env_scaffolded = True

deps = [
    '"fastapi>=0.110",',
    '"pydantic>=2.0",',
    '"uvicorn[standard]>=0.27",',
]
if has_sqlserver:
    deps.append('"pymssql>=2.3.0",')
if has_postgres:
    deps.append('"psycopg[binary]>=3.2",')
if has_jwt_bearer:
    deps.append('"pyjwt[crypto]>=2.8",')
deps_block = "\n".join(f"    {d}" for d in deps)

content = f'''\
# Generated by archascode — re-run /archascode:init to regenerate.
# Remove this header to take ownership of this file.

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "{name}"
version = "{version}"
description = "{description}"
requires-python = ">=3.12"
dependencies = [
{deps_block}
]

[tool.hatch.build.targets.wheel]
only-include = ["src"]
sources = ["src"]
'''

with open("pyproject.toml", "w") as f:
    f.write(content)

print("HAS_SQLSERVER=1" if has_sqlserver else "HAS_SQLSERVER=0")
print("HAS_POSTGRES=1" if has_postgres else "HAS_POSTGRES=0")
print("ENV_SCAFFOLDED=1" if env_scaffolded else "ENV_SCAFFOLDED=0")
PY
) || { echo "Failed to write pyproject.toml. Aborting." >&2; exit 1; }
```

Then print one line:

- sqlserver detected → `✓ pyproject.toml written (sqlserver → pymssql + aac script)`
- postgres detected  → `✓ pyproject.toml written (postgres → psycopg + aac script)`
- otherwise        → `✓ pyproject.toml written (base deps)`

Then, if `ENV_SCAFFOLDED=1` appeared in `PY_OUT`, print:

```
✓ added default 'dev' environment (memory, no auth) — architecture.yml updated; select 'dev' in the API Explorer to start it once rendered
```

If `ENV_SCAFFOLDED=0` (or `spec/architecture.yml` doesn't exist yet — the
greenfield case), print nothing further here.

### Step 4 — note `pyproject.local.toml` deprecation

If `pyproject.local.toml` exists, print:

```
NOTE: pyproject.local.toml exists. This file is deprecated.
Copy any [project.dependencies], [project.optional-dependencies], or
[tool.*] sections you want to keep into pyproject.toml (you'll need to
remove the `# Generated by` header at the top to take ownership), then delete
pyproject.local.toml.
```

The skill does NOT modify or delete `pyproject.local.toml` — the hand-
merge is the user's call. Printed once per `/archascode:init` invocation.

### Step 5 — ensure `.gitignore` covers `.venv/`, `__pycache__/`, and `.env` files, keeps `seeds/` tracked, and (when `ui:` is declared) keeps the UI dist tracked

If `.gitignore` exists, check whether it already ignores `.venv/`
(accept any reasonable anchored form — `.venv`, `.venv/`, `/.venv`,
`/.venv/`). If not, append:

```
# Local virtualenv managed by /archascode:init.
.venv/
```

Then independently check whether it already ignores `__pycache__/`
(accept `__pycache__`, `__pycache__/`, `**/__pycache__`,
`**/__pycache__/`). If not, append:

```
# Python bytecode caches from the rendered app.
__pycache__/
```

Then independently check whether it already ignores the `.env` files.
Accept a reasonable existing form — a bare `.env` line plus a
`.env.*` line, or an equivalent that ignores both the base `.env` and
the per-environment `.env.<env>` overlays. The required end state is:
`.env` and `.env.*` ignored, **but** the committed
`.env.<env>.example` templates re-included. If that is not already
present, append:

```
# Local environment files (secrets). The base .env and
# per-environment .env.<env> overlays are ignored; the committed
# .env.<env>.example templates are not.
.env
.env.*
!.env.*.example
```

When checking an existing `.gitignore`, if it ignores `.env`/`.env.*`
but does **not** re-include `.env.*.example` (so the committed examples
would be ignored), append the `!.env.*.example` negation line on its
own. Order matters: the `!` negation must come **after** the `.env.*`
ignore for git to honor it — append it at the end of the block / file.

Then independently check whether the existing `.gitignore` ignores
`seeds/` (accept any form — `seeds`, `seeds/`, `/seeds`, `/seeds/`) **or**
the legacy `snapshots/` spelling (accept any form — `snapshots`,
`snapshots/`, `/snapshots`, `/snapshots/`). Older projects scaffolded
before seed data was autoloaded at boot (or before the directory was
renamed from `snapshots/` to `seeds/`) carry such a rule, typically with
a comment citing the old `/admin/snapshot` endpoints. Delete the rule and
its accompanying comment (whichever spelling matched): `seeds/` must be
committed, because the generated app autoloads it at boot
and a build-from-repo PaaS deploy can only autoload
what git carries. Tell the user seed data is now tracked and, if a
`seeds/` directory already exists, remind them to `git add seeds/` so the
seed data ships with the next push.

Then, when `snapshots/manifest.json` exists on disk and `seeds/` does
not, this is a legacy project predating the seed-vocabulary rename: run
`git mv snapshots seeds`
(plain `mv snapshots seeds` if `snapshots/` is untracked), and tell the
user the seed-data directory was renamed and the migration is
done.

Then, **when `spec/architecture.yml` declares a top-level `ui:` block**,
guard the UI build artifact the same way: resolve the dist
path from `ui.dist` (or the default `ui/dist` if `ui: {}` or `dist` is
omitted), then check whether that path is ignored by **any** applicable
`.gitignore` — the root `.gitignore` **and** every `.gitignore` on the
path between the project root and the dist directory (e.g.
`ui/.gitignore` — frontend scaffolds commonly ship a `dist` ignore line
there). This is the same failure shape as the
`seeds/`-ignored bug above, caught here at authoring time instead of
discovered later as a silently UI-less deploy: an ignored dist means
`git push` ships a repo whose committed backend has no frontend inside
it, while `npm run build` and the local Vite dev server keep working
right up until the deploy, giving no local signal anything is wrong.

For each `.gitignore` on that path (root, plus any nested one above the
dist directory), look for a rule that matches the dist directory or any
ancestor of it (accept the same "reasonable anchored form" latitude as
the other sub-checks — bare name, trailing slash, leading slash,
`**/`-prefixed). If found and unambiguous (a rule that ignores exactly
the dist directory, or a directory it is nested under, e.g. a bare
`dist` or `dist/` line in `ui/.gitignore` when `ui.dist` is `ui/dist`),
delete the rule and its accompanying comment, the same as the
`seeds/` sub-check. If the match is ambiguous — a broad pattern
whose intent isn't clearly "ignore the UI build output" (e.g. a glob
that also plausibly covers something else) — do not delete it; instead
flag it to the user by name (file + line) and explain why it needs
attention. Either way, tell the user what changed or what to check, and
why: **an ignored dist silently strips the UI from every
build-from-repo deploy while the local dev server keeps working.**

Once the dist is confirmed tracked (or flagged), remind the user of the
deploy ritual: `npm run build` (or the project's equivalent)
→ commit the changed dist → `git push`. Also remind them that because
the UI and the API now share one origin in the deployed app, client
route names must not collide with generated endpoint paths —
`/openapi.json` is the reserved list to check against (the API's own
routes, `/docs`, and `/openapi.json` always win over the UI mount by
registration precedence; a route the UI names identically to a
generated endpoint will get JSON instead of the app on a refresh).

If `.gitignore` does not exist, create it with all three blocks (plus
the `ui:`-gated dist check above, which is a no-op with nothing to
create when there is no existing `ui/.gitignore` to inspect and the
freshly created root `.gitignore` carries no dist-ignoring rule to
begin with).

### Step 6 — create or sync the venv

```bash
[ -d .venv ] || uv venv
uv sync
```

If `uv sync` exits non-zero: print uv's stderr verbatim and stop. Do
not classify the error or retry.

### Step 7 — verify the lifecycle script imports (when applicable)

Only check when `aac.py` exists at cwd (i.e. render has happened
post-spec). The app is launched by file path (`uv run python aac.py up`),
so there is no console-script entry point to verify; instead smoke-check
that the venv can import the lifecycle script's deps:

```bash
if [ -f aac.py ]; then
  uv run python -c "import aac" || { echo "aac.py failed to import under the venv; uv sync output above" >&2; exit 1; }
fi
```

If `aac.py` is missing, the project is in the pre-render or
post-spec-edit state — skip the check silently.

### Step 8 — terse success

Print one line per step that did work, then a mode-aware final line.

If `aac.py` exists:

```
Done. Next: start the API from the API Explorer, or `/archascode:seed` to populate data first
```

Else if `spec/architecture.yml` exists:

```
Done. Next: /archascode:apply
```

Else (true greenfield):

```
Done. Next: /archascode:analyze <prd.md> to draft spec/architecture.yml (or write it by hand), then /archascode:apply
```

## What this skill does NOT do

- **Modify `pyproject.local.toml`.** It prints a deprecation prompt
  when the file is present; the migration is hand-done by the user.
- **Re-scaffold a user-owned pyproject.** If the header sentinel is
  absent, the file is left alone (warning printed; venv synced
  against whatever the file declares).
- **Run `archascode render`.** Render is its own step. Aligned with
  the `terraform init` → `terraform plan` → `terraform apply` model.
- **Activate the venv.** Skills run in subprocesses and can't modify
  the parent shell. The launch form (`uv run python aac.py up`) is the
  answer post-render.
- **Generate or check a lockfile.** No `uv lock` today.
- **Install `aac` or `archascode` globally** via `uv tool install`.
  Per-venv is the right scope.
- **Auto-detect drift** when the spec's adapter set changes. Discipline
  is documented; the failure mode (`ModuleNotFoundError`) is loud.
- **Run before `/archascode:apply` or `aac.py up`** without the user asking.
  Explicit invocation only.

## Failure modes (v1)

| Symptom                                                            | Behavior                                                                                       |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `uv` not on PATH                                                   | Print install instructions; stop.                                                              |
| `uv run --with 'ruamel.yaml'` fails (network down on first run, resolver error) | Print uv's stderr verbatim; stop. Do not classify or retry — same posture as `uv sync`.        |
| `spec/architecture.yml` is malformed YAML                          | Print Python's parse error; stop. User fixes the spec and re-invokes.                          |
| `spec/architecture.yml` write fails (e.g. permission denied) during the `environments:` scaffold | Print the error; stop before writing `pyproject.toml`. The spec is left as it was on disk (the failed write is `ruamel.yaml`'s, not a partial one). |
| `pyproject.toml` present without a `# Generated by` header                | Print warning; skip pyproject write; sync venv anyway.                                          |
| `uv venv` fails                                                    | Print stderr verbatim; stop. Do not retry.                                                     |
| `uv sync` fails (install failure, network, etc.)                   | Print stderr verbatim; stop. Do not classify or retry.                                         |
| `aac.py` exists but `import aac` fails under the venv               | Print uv's last output; stop. Likely the editable install is misconfigured or a runtime dep (e.g. `pymssql`) failed to install. |
| `ModuleNotFoundError` at app start after a spec change             | Out of scope here — surface is `aac.py up`. Fix: re-run `/archascode:init` (the spec's adapter set changed and the venv is stale). |

The skill does not retry. The user re-invokes after fixing whatever
the error surfaced.
